# Operating-Path Detector Coverage — Honest Ceiling Table

## What "fires in the pipeline" means

"LIVE-in-pipeline" means every required spine leg for the detector is written by a real agent `run()` (called from `scan_run` in `packages/runtime/src/nexus_runtime/scan_pipeline.py`), the edges land in a shared `SemanticStore`, `correlate_all` runs the cross-agent bridge resolvers, and `analyze` calls `AttackPathRanker.find_all` — the full `scan_run → correlate → rank` chain. This is proven against offline feeds and fixtures (inventory JSON, VPC flow logs, NVD snapshots, Falco feeds, manifest directories, SCM connectors). "LIVE-in-pipeline" does NOT mean live cloud accounts: pointing any agent at a real AWS/Azure/GCP account is `NEXUS_LIVE_*`-gated operator work. The pipeline proves the graph logic; live emission proves operational connectivity.

1. **`find_internet_exposed_host_vulnerable`** — host-direct `VULNERABLE_TO` (Trivy host/VM scan on instance ARN) not wired; EC2 `is_public` from injection seam only.

3. **`find_exposed_kms_key`** — `cloud_posture/kg_writer.record_kms_keys` exists but is never called from `agent.py run()`; no live AWS KMS reader; no pipeline feeder writes KMS spine nodes.

## Known Scope Limits

### Stored-secret scope (AWS keys only)

`find_stored_secret_to_data` fires only for AWS AKIA/ASIA-prefixed access key IDs. `stored_secret_grants` (the ECS env-value extractor in `cloud_posture/tools/stored_secrets.py`) applies `_AKIA_RE = re.compile(r"(AKIA|ASIA)[0-9A-Z]{16}")` and ignores all other credential shapes. GitHub PATs, database passwords, GCP service-account keys, and other non-AWS credentials in ECS container environment values are **undetected and not fingerprinted**.

### Cloud-posture topology: pipeline-proven, live-reader deferred

EC2 and ECS topology (`is_public`, `private_ips`, `iac_artifact`, `RUNS_IMAGE`, `ASSUMES`) is written via the **injectable-workload seam** (`scan_run` passes `cloud_ec2_workloads` / `cloud_ecs_workloads` to `cloud_posture_run`). The live-boto path (`read_ec2_workloads` / `read_ecs_workloads` from real AWS credentials) is not wired: `cloud_posture/agent.py run()` receives `None` for those params when the pipeline omits them, and the `_write_topology_to_kg` helper no-ops. The detectors that depend on this topology are pipeline-proven with injected workloads; live-cloud emission requires a boto-client wiring follow-on.

### Multi-cloud KMS/SQL/VM: writer exists, never called

`multi_cloud_posture/tools/kg_writer.py` defines `record_kms_keys`, `record_sql_instances`, `record_vm_instances` (the B-1/B-2 Track-B methods). None of these methods are called from `multi_cloud_posture/agent.py`. Additionally, `multi_cloud_posture` is not wired as a feeder in `scan_pipeline.py`. The Azure/GCP KMS, SQL, and VM spine nodes are therefore never written; the three KMS/DB detectors cannot fire on Azure or GCP resources.

### K8s pod reachability (POD_CAN_REACH): offline feeds carry no data

`k8s_posture/kg_writer.record_pod_reachability` writes `POD_CAN_REACH` edges (W4 pod-to-pod lateral movement). This is not used by any current `find_*` detector in `kg_query.py`, so it does not affect any row in the table above. Observed network reachability from offline manifests is structurally unavailable; live-cluster-only.

### Live cloud accounts: operator-gated

Every LIVE-in-pipeline verdict is proven against feeds and fixtures with a real Postgres `SemanticStore`. Pointing any agent at a live AWS/Azure/GCP account requires the `NEXUS_LIVE_*` environment gates. The pipeline's correctness is feed-proven; live-account emission is operator work.

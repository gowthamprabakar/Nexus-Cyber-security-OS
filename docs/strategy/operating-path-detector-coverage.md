# Operating-Path Detector Coverage — Honest Ceiling Table

## What "fires in the pipeline" means

"LIVE-in-pipeline" means every required spine leg for the detector is written by a real agent `run()` (called from `scan_run` in `packages/runtime/src/nexus_runtime/scan_pipeline.py`), the edges land in a shared `SemanticStore`, `correlate_all` runs the cross-agent bridge resolvers, and `analyze` calls `AttackPathRanker.find_all` — the full `scan_run → correlate → rank` chain. This is proven against offline feeds and fixtures (inventory JSON, VPC flow logs, NVD snapshots, Falco feeds, manifest directories, SCM connectors). "LIVE-in-pipeline" does NOT mean live cloud accounts: pointing any agent at a real AWS/Azure/GCP account is `NEXUS_LIVE_*`-gated operator work. The pipeline proves the graph logic; live emission proves operational connectivity.

## Bottom Line

**24 LIVE-in-pipeline / 0 live-cloud-gated / 0 BLOCKED** (24 + 0 = 24)

22 detectors reached 22/22 (PR #797–#801). **Cycle 3 (branch `feat/cycle3-moat-productization`, off main+#801) productizes the moat and adds 2 deepened detectors**, reaching 24/24. (Independent of #802, which adds its own 2 — expect a coverage-doc union at merge.)

**Moat productization — durable + exportable (the headline).** The ranked cross-agent attack paths, previously transient (in-memory `list[AttackPath]` → Markdown at the CLI), are now:

- persisted as durable **`ATTACK_PATH` graph nodes** (`AttackPathWriter`) — cross-scan-tracked via a stable key `attackpath:sha256(path_type|sorted(entities))[:16]` with set-once `first_seen` / bumped `last_seen`; run-over-run dedup is free (ADR-022 node upsert + edge UNIQUE index). `CONTRIBUTES_TO` edges from each entity + `PART_OF_PATH` to the sink.
- emitted as **OCSF 2005 Incident Findings** (`build_incident_finding`) — SIEM-exportable; `finding_info.uid` == the node key so graph and SIEM dedup on the same identity; evidence carries ids / CVE ids / data-types only (no plaintext secrets).
- wired into `analyze` behind a `persist` flag (`scan_run` sets `persist=True`; CLI + existing tests default `persist=False` → zero side-effects). Proven cross-scan (twice-run e2e: one node, `first_seen` held, `last_seen` bumped).

**2 deepened detectors** (commodity single-signal → real toxic combination; both offline-provable, both subsume their shallow parent per-subject):

- **`find_rbac_escalation_to_cloud_data`** (sev 84) — a cluster-admin service-account (`BINDS` an `is_admin` role) that ALSO reaches cloud data (`IRSA_MAPPING → role → HAS_ACCESS_TO → resource → EXPOSES_DATA`). K8s admin + cloud-data breach; dominates both `rbac_privilege_escalation` and `k8s_escape_to_cloud_data`.
- **`find_exposed_kms_key_over_data`** (sev 80) — a public KMS key (`is_public`) that ALSO `EXPOSES_DATA` to a classification. The encryption boundary is internet-open AND guards classified data — worse than a bare exposed key.

**Deferred to Cycle 4 (honest):** public-RDS→PII — no producer writes an `rds-instance → DATA_CLASSIFICATION` edge today (`record_rds_instances` writes the node only); that's collection wiring, not productization.

## Known Scope Limits

### Stored-secret scope (AWS keys only)

`find_stored_secret_to_data` fires only for AWS AKIA/ASIA-prefixed access key IDs. `stored_secret_grants` (the ECS env-value extractor in `cloud_posture/tools/stored_secrets.py`) applies `_AKIA_RE = re.compile(r"(AKIA|ASIA)[0-9A-Z]{16}")` and ignores all other credential shapes. GitHub PATs, database passwords, GCP service-account keys, and other non-AWS credentials in ECS container environment values are **undetected and not fingerprinted**.

### Cloud-posture topology: pipeline-proven, live-reader deferred

EC2 and ECS topology (`is_public`, `private_ips`, `iac_artifact`, `RUNS_IMAGE`, `ASSUMES`) is written via the **injectable-workload seam** (`scan_run` passes `cloud_ec2_workloads` / `cloud_ecs_workloads` to `cloud_posture_run`). The live-boto path (`read_ec2_workloads` / `read_ecs_workloads` from real AWS credentials) is not wired: `cloud_posture/agent.py run()` receives `None` for those params when the pipeline omits them, and the `_write_topology_to_kg` helper no-ops. The detectors that depend on this topology are pipeline-proven with injected workloads; live-cloud emission requires a boto-client wiring follow-on.

### Multi-cloud KMS/SQL: now cross-cloud via multi-cloud-posture feeder

`multi_cloud_posture/tools/kg_writer.py` `record_kms_keys` and `record_sql_instances` are now called from `multi_cloud_posture/agent.py` and wired into `scan_pipeline.py` via `ScanSources.mc_kms_keys` / `mc_sql_instances`. Both methods stamp the same `kind=kms-key`/`rds-instance` + `is_public` markers on Azure/GCP-keyed nodes, so `find_exposed_kms_key` and `find_exposed_database` fire cross-cloud (AWS + Azure/GCP). VM instances (`record_vm_instances` via `ScanSources.mc_vm_instances`) are wired identically but no current detector queries `kind=vm-instance`; that coverage is structural groundwork only.

### K8s pod reachability (POD_CAN_REACH): offline feeds carry no data

`k8s_posture/kg_writer.record_pod_reachability` writes `POD_CAN_REACH` edges (W4 pod-to-pod lateral movement). This is not used by any current `find_*` detector in `kg_query.py`, so it does not affect any row in the table above. Observed network reachability from offline manifests is structurally unavailable; live-cluster-only.

### Live cloud accounts: operator-gated

Every LIVE-in-pipeline verdict is proven against feeds and fixtures with a real Postgres `SemanticStore`. Pointing any agent at a live AWS/Azure/GCP account requires the `NEXUS_LIVE_*` environment gates. The pipeline's correctness is feed-proven; live-account emission is operator work.

## Ranking

Confirmed attack paths returned by `AttackPathRanker.find_all` are now ordered by **expected loss**, not a flat `_SEVERITY` constant. Each path's score is:

```
expected_loss = sink_p (noisy-OR across path legs) × blast_radius
```

where `sink_p` is derived from `path_priors.leaf_probability` incorporating **real KEV/EPSS exploitability**, and `blast_radius` is estimated from the data-classification sensitivity and scope of the sink node. `build_report_card` uses the same `rank_by_expected_loss` comparator, so the fleet scorecard ordering matches the per-scan ranking.

**KEV/EPSS provenance (corrected).** The exploitability signal is written onto graph CVE nodes by the **vulnerability** graph writer (`vulnerability/kg_writer.py:record_scan_results`), not by threat-intel (which emits KEV/EPSS only as OCSF `IndicatorScore`, never onto graph nodes). Each CVE node carries `kev` (bool) and `epss_score` (float); the six CVE-bearing detectors read those keys → `AttackPath.kev` / `AttackPath.epss` → `leaf_probability` (KEV floors route-probability at ≥0.9; EPSS wins when present). Sourcing: the pipeline injects `ScanSources.vuln_kev_cve_ids` / `vuln_epss_scores` (offline/tested path); a live `enrich=True` run auto-sources from the agent's `is_kev` (CISA KEV) + `nvd_enrich` (FIRST.org EPSS) tools, 24h-cached.

**Honest correction (supersedes the earlier "written by threat-intel" claim).** Through PR #801 this lift was _inert in the running pipeline_: the writer stamped the property under key `kev` while the detectors read `kev_listed` (a key mismatch), `run()` never passed a KEV catalog to the writer, and EPSS was never written to any node. #801's ranking tests planted `kev_listed`/`epss_score` directly onto node properties, so they passed while nothing in the pipeline wrote them (green-for-the-wrong-reason). This branch closes all three breaks; a through-the-real-writer e2e (`test_scan_run_kev_reaches_confirmed_path`) now proves a KEV-flagged CVE reaches a confirmed path with `.kev is True` in `scan_run`.
